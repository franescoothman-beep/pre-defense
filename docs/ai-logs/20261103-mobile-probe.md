## 3. 设计决策（含被否决的方案）

### 3.1 为什么用 CDP，不用 `--window-size` 或 iframe

两条弯路 11-02 都走过，`progress.md:494-495` 有记录，这次直接绕开：

| 方案 | 问题 | 结论 |
|---|---|---|
| `--window-size=400` + `--screenshot` | 无头 Edge 窗口宽有下限，**截图里"被切"是裁出来的假象，不是真 400px 视口** | ❌ 用它量移动端等于没量 |
| iframe 探针 | 11-02 靠它抓到真凶（`.ribbon` / `.mock-banner`），但跨源要开 `--disable-web-security` | ⚠️ 能跑，但为了量尺寸拆安全栏杆 |
| **CDP `Emulation.setDeviceMetricsOverride`** | 唯一能拿到真实 400px 视口的办法 | ✅ **采用** |

11-02 记录"CDP 直连两次都 `CDP 未就绪`"——那不是 CDP 不可用，是**没等端口真正绑上就去连**。
本脚本改成轮询 `/json/list` 直到出现 page target（最长 15s），把这个坑填掉了。

### 3.2 不新增依赖

WebSocket 用 Node 22+ 的全局 `WebSocket`（`engines: node >=22.13.0` 已满足），
`node:sqlite` 用 `createRequire` 同步取。**零新依赖**（铁律 4）。

### 3.3 页面清单自动发现，不写死

写死路径会因为库里报告 id 每次重跑都变而迅速失效，探针就变成"全绿但什么都没测"。
改为从 `data/app.db` 读：材料页取 4 份有 claims 的、会话页取 2 个未出报告的、
报告页取最新 1 份，加固定页 `/` `/upload`。

## 4. Bug 与修复过程（真实，三条）

### Bug 1（P1）：ESM 里用 `require` → `require is not defined`

**报错原文**：
```
✖ 探针失败： require is not defined
```

**根因**：`package.json` 有 `"type": "module"`，`.mjs` 是 ESM，**没有全局 `require`**。
我在 `require_node_sqlite()` 里写了 `require('node:module')` 去取 `createRequire`——这是先有鸡还是先有蛋。

**修法**：在文件顶部 `import { createRequire } from 'node:module'`，
函数内直接用 `createRequire(import.meta.url)('node:sqlite')`。

**教训**：ESM 项目里"顺手写 require"不报编译错，只在运行到那一行时才炸。

### Bug 2（P0，最危险）：探针 9/9 全绿，但**根本没测到报告页**

**现象**：第一版跑完输出 9 个 ✔，但我注意到报告页那行是：

```
✔ /report/9eb9c062-...    clientW=400 scrollW=400 正文47字
```

**正文只有 47 字** —— 那是「正在读取报告…」的骨架屏。报告页是全站最宽的布局
（看板 3×4 + 两栏 + 引用卡片），**最该测的页面恰恰被漏掉了**。

**根因**：我的"渲染完成"判据是「正文长度连续 4 次不变」。
但**骨架屏本身就是稳定的**——它一直显示「正在读取报告…」，长度恒为 47。
所以判据在数据回来之前就满足了，探针量到的是一张空壳。

**为什么这个 bug 比 Bug 1 危险得多**：Bug 1 会炸，人立刻知道。
Bug 2 不会炸，它输出漂亮的 9/9 全绿，**让整件事看起来完成了**。
如果没有多看一眼那个"47 字"，这个探针就会以"已验证通过"的姿态进入仓库，
下次真出溢出时它依然会报 ✔。

**修法**（三条判据缺一不可）：
1. 正文长度稳定
2. **不在骨架态** —— 页内正则 `/正在读取报告|正在加载|正在解析|正在抽取|正在排席位|正在生成报告|正在发言/` 命中即视为未就绪
3. 至少等 1.2s（防 SSR 首帧就稳定、JS 还没跑）

并且**把"没测到"与"通过"分开报告**：新增 `unmeasured` 状态，输出 ⚠ 与退出码 2，
不再混进 ✔ 的计数里。

**修复后**：报告页正文 **47 字 → 4650 字**，是真内容了。

### Bug 3（P1）：一次 `edit` 误删 `if` 行，造成语法断裂

改"未测到"分支时，`old_string` 多含了一行 `if (unmeasured.length > 0) {`，
替换后那个 `if` 被吃掉，留下 `console.log('')` 孤立在函数体里。

**修法**：把 `if` 行补回。**教训**：`edit` 的 `old_string` 边界要贴着真改动，
不要"顺手多带一行"——多带的这一行不会报错，只会让上下文错位。

## 5. 负向对照（`--self-test`）：证明探针真的会报错

**动机**：一个永远输出 ✔ 的探针等于没有探针。它可能因为量了假视口（`--window-size` 那条弯路）、
也可能因为判定条件写反（`>` 写成 `<`），而**两种失效都长得和"真的没问题"一模一样**。

**做法**：在当前页注入一个 `width: 600px` 的绝对定位元素，立刻重测，
**必须**测出 `scrollW > clientW`；再移除它确认恢复绿。

**结果**（`npm run probe:mobile -- --self-test`）：
```
[自检] 注入 600px 元素 → ✔ 探针测出了溢出（判定链路是活的）
```
9 个页面逐个自检全部通过 → 判定链路是活的，那些 ✔ 才有意义。

## 7. 我的修改（与 AI 输出的差异）

AI 首版给的是"能跑"的脚本，但有 Bug 2 那个致命缺陷。以下判断是我做的：

1. **不接受"9/9 全绿"作为完成信号** —— 坚持看每行正文长度，才发现报告页只有 47 字。
   如果只看结论行，这个探针会以坏的状态入仓。
2. **要求加负向对照** —— AI 没主动想到"怎么证明探针本身有效"。
   这个自检现在是我对任何"验证脚本"的默认要求。
3. **要求把"没测到"与"通过"分开** —— 而不是笼统地算进通过率。
   一个 8/9 通过的诚实结果，比 9/9 但有一个是空壳更有价值。
4. **坚持测 280px** —— 400px 是产品要求的下限，但测更窄能证明修复不是"刚好卡线"。
