## 我的判断与取舍

### 取舍 1：不装 OBS / ffmpeg，先做「结构化走查」

我本想直接开录。但发现本机**没有 OBS、没有 ffmpeg**，而装这些东西要下载几十 MB、还得调场景配置——那是正式录制前的事，不该堵住试录。

所以我换了做法：**用 CDP 驱动浏览器，按视频脚本的真实点击路径走一遍，逐屏截图 + 记时间码**。这等价于「录了一遍，但产物是截图和表格而不是 mp4」。它的好处是：每一步的耗时精确到 0.1 秒（录像只能靠肉眼估），而且能自动化重跑。

这不是偷懒，是**把试录的目的和试录的形式分开**。目的（发现问题）达成即可，形式（有个 mp4）留给正式录制。

### 取舍 2：坚持「真人点击」，不做接口快进

第一版走查为了快，直接用 `POST /api/sessions/:id/answer` 推状态机。跑完 106.9 秒，全绿。

但报告页写着「**主问 1/3**」「共问 2 次」——它只问了一位评委。因为**浏览器页面自己没前进**，只有数据库被改了。

这意味着：这条走查既没测到点击耗时，也没测到追问态渲染、评委切换动效、回答框出现时机——而这些恰恰是「人手走完」的全部内容。

**试录的价值就在「人手」两个字。** 绕过去等于什么都没验，只验了 API 通不通（那个 11-02 已经验过了）。

所以我推翻重写：全程操作真实 DOM。

### 可读性（本次最重要的结论）

| 页面 | 最大字 | 正文 | 最小字 |
|---|---|---|---|
| 首页 | 62px | **17px** | 11px |
| 素材页 | 34px | **13.5px** | **10px** |
| 报告页 | 26px | **11px** | 11px |

1080p 视频里正文应 ≥18px、脚注 ≥15px。**现在全部不达标。**

三种放大方案实测（截图尺寸均为 1920×1080）：

| 方案 | 结果 | 判定 |
|---|---|---|
| CSS 视口 1280×720 + `deviceScaleFactor 1.5` | 字放大约 1.5 倍、**依然锐利**、布局按窄屏重排、无横向溢出 | ✅ **采用** |
| CSS `zoom: 1.5` | 字变大但不重排，组件内部易挤 | ⚠️ 备选 |
| `Emulation.setPageScaleFactor` | 仅视觉放大，**画面被裁** | ⛔ 否决 |

→ 正式录制：浏览器 `Ctrl` + `+` 两次到 **150%**，OBS 画布仍是 1920×1080。

## Bug 与修复过程

### Bug 1：测量脚本本身在骗我（P1）

**现象**：`_fontprobe.mjs` / `_dprprobe.mjs` 在 100%/125%/150%/175% 四档下，全部报告「正文 11px、最小 11px」——**四档数字一模一样**。

**如果就此收工**，我会得出「缩放没用」的结论，然后带着一份看不清的视频去录制。

**破案**：取最小字号时没排除固定尺寸的装饰元素。屏幕上 11px 的 **MOCK 角标**永远存在、永远是最小值，所以「最小 11px」恒定。而「正文」选择器 `p, .serif, main p` 在报告页首屏匹配到的是看板图例（也是 11px），不是两栏里的说明段。

**修法**：不看数字看截图。`dpr150-1920.png` 目视确认文字明显变大且锐利 → 方案成立。

**教训（第二次同类）**：这是今天第二次「工具全绿/全稳，结论是假的」。第一次是骨架屏判据（`docs/ai-logs/20261103-mobile-probe.md` Bug 2），这次是固定元素干扰测量。**共同点是：判据/选择器写了，但没有对照检查它是否指向我以为的那个东西。** 以后任何「量一个值」的脚本，都要先验证它量到的是目标元素（打印文本片段对照）。

### Bug 2：`1536×864` 那档可见字为 0

`_zoomprobe.mjs` 的输出里，125% 档显示「可见字 0」——页面根本没加载完就被量了。

**但没有影响结论**，因为我是拿截图判的。这里记一笔：**数字异常（0、负数、全相等）时不要绕过，要先确认是测量问题还是现象问题。**
