# 2026-10-31 · 阶段 1：解析与锚点接线（上传 → PDF/DOCX → blocks → 落库）

## 目标
1. `lib/security.ts`：S1 上传白名单 + 体积上限 + 魔数校验，落盘名只用 uuid（S2）
2. `lib/extract.ts`：PDF 逐页取文本 → `pagesToBlocks`（page 有值）；DOCX 全文 → `paragraphsToBlocks`（page=NULL）
3. `POST /api/docs`：校验 → 解析 → 落盘 → 事务写 `documents` + `blocks`
4. 上传页（方向 E）：拖拽 + 进度 + 「已解析 N 页 / M 块」+ 前 3 块预览
5. 图片型 PDF 返回可读错误而非 500（不硬做 OCR）

## Prompt 原文（要点）
- "只做到「解析 + 锚点」为止，不调 LLM"
- "S1 校验：白名单 + MIME/魔数双检 + ≤20MB；落盘名 = uuid + 扩展名"
- "图片型 PDF 明确提示不支持（不硬做 OCR）"
- "docx 走 flow 模式不报错，page 为 NULL 且 UI 正确显示"

## 我的判断与取舍（这轮真正的产出）

1. **指令包 §2 有三处过期，先修文档再写代码**
   - 原文写 `.pdf/.docx/.pptx` + `officeparser` → 与 v2.1.2 决策冲突（PPTX 不做、DOCX 走 mammoth）
   - 按 `开发流程详细文档.md §4 阶段 1` 校正，并补上 `lib/security.ts` / `lib/extract.ts` 两个拆分
   - 理由：照抄原文会装进一个 30MB+ 的错误依赖（officeparser 拖 tesseract.js WASM OCR + 第二份 pdfjs）

2. **纯函数层不动，只做接线** —— 阶段 0 已有 46 个单测钉死 `parse`/`locator` 的行为。
   本阶段新增的是 `extract.ts`（唯一接触 pdfjs/mammoth 的地方），让"格式库的坑"不污染"解析逻辑的正确性"。

3. **补了一个 `dropRunningHeads()` 纯函数**
   - 论文每页顶部重复论文题目、底部重复「第 X 章」；
   - 判据不是"长什么样"，而是**同一短句在 ≥30% 页里重复**——正文句子不会在几十页里一字不差重复；
   - 不处理的后果：这些行会变成可被 `block_idx` 命中的"原文"，模型引用一句毫无信息量的重复页眉，
     直接污染引用命中率的可信度。

## Bug 与修复过程（真实记录，按发现顺序）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `npm i mammoth` 后 `npm run build` 报 `Failed to load SWC binary` | npm 把 `optionalDependencies` 里的 `@next/swc-win32-x64-msvc` 削掉，且版本被改成 `^15.5.28` | 重装并锁回精确版本 `15.5.28` |
| 2 | `next build` 报 `database is locked`（ERR SQLITE 261） | `lib/db.ts` 在**模块顶层**建连接并执行 `PRAGMA journal_mode = WAL`；构建期多 worker 并发 import 同一模块，第一个在抢写锁，其余直接失败 | 连接改**懒加载**（首次 `q.*` 才建）；先设 `busy_timeout` 再碰写锁；WAL 前先读 `PRAGMA journal_mode`，已是 WAL 就不用再抢锁 |
| 3 | 上传 6.1MB PDF 返回 **500 且响应体为空** | `req.formData()` 之后，Next 15 运行时把 File 背后的 ArrayBuffer detach 了；`new Uint8Array(await file.arrayBuffer())` 抛 `Cannot perform Construct on a detached ArrayBuffer`，且异常在框架请求体管线里抛出，route 的 try 接不住 | 不再用 `formData()`，改为**读原始 `req.body` 流 + 自己解析 multipart**（`lib/multipart.ts`）；同时给 route 加最外层兜底，保证任何异常都返回 JSON |
| 4 | 自写的 multipart 解析器对多 part 请求返回 null | `headerEnd` 写成 `new Uint8Array([CRLF, CRLF])`，而 `CRLF` 是**单字节 13**，等于在找连续两个 `\r`，永远找不到空行 | 改为 `[CRLF, LF, CRLF, LF]`（即 `\r\n\r\n`），并补 8 个单测（含 256 字节二进制、中文文件名、截断 body） |
| 5 | 同一个解析器 `contentStart` 少了 2 字节 | 误以为 `headEnd` 指向空行第一个 `\n`，实际指向 `\r\n\r\n` 的起点 | `headEnd + 4` |
| 6 | 用 PowerShell 内联写含中文的 JS/Python 脚本，引号与 GBK 双重编码把文件写坏 | PowerShell 解析器对 `"` 与 `[` 敏感，且默认编码会损坏中文 | 一律改用 `write` 工具落盘脚本文件，再 `node 脚本` 执行（**对应 CLAUDE.md 铁律 8**） |

> **#3 是本阶段最有价值的一条**：它只在**大文件 + 生产模式**下复现（37KB 的 DOCX 一直正常，6.1MB 的 PDF 必挂），
> 属于"看起来能跑、真实材料一上传就炸"的典型。如果只测小文件，这个 bug 会一路带到省赛演示现场。
