# 2026-10-31 阶段 3 第二块：SSE 流式后端（`GET /api/sessions/:id/stream`）

## 目标

只做后端流，不做前端页面（用户明确要求）。

1. `lib/sse.ts`：SSE 事件编码 + 上游流解析 + 增量 JSON 字段解包（纯函数，可单测）
2. `lib/llm.ts`：新增 `callLLMStream`（`stream: true`，与 `callLLM` 共用预算池与日志）
3. `lib/session.ts`：会话读取与"当前该问什么"的装配（纯查询，不写库不调模型）
4. `lib/prompts/question.v1.ts` + `QuestionOut`：单次提问 prompt（每问一次，流式出题）
5. `GET /api/sessions/:id/stream`：`meta` / `token` / `done` / `error` 四事件

## 契约（`开发流程详细文档.md §3.6`）

```
event: meta    data: {"persona":"…","qIndex":2,"claimId":"c_12","blockIdx":18,...}
event: token   data: {"t":"样本"}
event: done    data: {"turnId":"t_7","state":"ASKING","progress":{...}}
event: error   data: {"code":"timeout","fallback":"（评委停顿了一下，请再问一次）"}
```

## 我的判断与取舍

1. **首字节必须立刻发**。真实模型冷启动常 >1s，DoD 要求「首字 < 1.5s」。
   所以在响应开头先发一条注释行 `: ready`，让"连接建立 + 浏览器开始解析"立刻可观测。
   实测首字节 **38ms**，全流（含模型出字）约 0.9–1.6s。

2. **必须在服务端解包 JSON 外壳**。上游开着 `response_format: json_object`，
   增量形如 `{"question": "这三所`。原样透传会怎样？**前端会逐字显示 `{"question": "` 和结尾的 `"}`**——
   "评委在说话"演成"在看一段代码"，流式这个卖点当场变成 bug。
   为此写了 `createFieldStreamer`（极小的状态机，处理转义、`\uXXXX`、整键匹配）。

3. **重播不重复烧预算**。断线重连时若重新调模型，一场 3 问会花掉 6 次预算，
   而且用户会看到同一评委换了个问法（看起来像 bug）。重播路径直接吐库里存的 question，
   实测第二次 **6ms**（首次 1007ms）。

4. **`callLLMStream` 不做"重试 1 次"**。非流式的 `callLLM` 会重试，
   但流式已经把半句话给用户了，重试等于把前半句吞掉重来。改为**收流后统一 zod 校验**，
   失败发 `error` 事件让前端展示 fallback。

## Bug 与修复过程（真实记录）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | SSE 立刻返回 `error`（"内部错误"），且**服务端没有任何日志** | catch 分支只发 `error` 事件不 `console.error`，真堆栈无处可查 | 加 `console.error(..., code, err)`；这条后来写成了静态测试（`sse-route.test.ts`） |
| 2 | `no such column: target_claim_id` | `turns` 表压根**没有这一列**，但我在路由里按它查/插 | `lib/db.ts` 加列 + `ensureColumn()` 幂等迁移（`CREATE TABLE IF NOT EXISTS` 不会给旧表补列） |
| 3 | 同一份材料开到第 3 场时 `personas` 累积到 **9 条**，评委轮转错位 | `personas` 只按 `doc_id` 存，每建一次会话追加 3 条 | 加 `session_id` 列并迁移；建会话前清掉该 doc 旧人设；读取优先按 session，旧数据（`session_id is null`）回退 |
| 4 | **前端看到的是 `{"question": "…"}` 而不是评委的话** | 直接把上游原始增量推成 `token` 事件 | `createFieldStreamer('question')` 只吐字段值；最终写库也改用解包后的文本 |
| 5 | 问题文本末尾多一个 `}`（"…吗？}"） | `createFieldStreamer` 的字符循环在值收尾后**没有 break**，同 chunk 里剩下的 `}` 被继续追加 | 循环内 `if (phase === 'done') break;`。**这个 bug 只在特定切片大小下出现**（按 1 字切不暴露，按 5 字切暴露），所以测试按 1/2/3/5/7/100 六种粒度各跑一遍 |
| 6 | 重连时把**空白发言**重播给前端（一条空的问题） | SSE 先建占位 turn 再流式填问题；中途断线会留下 `question=''` 且 `answer=''` 的行，而"待回答"判定只看 `answer` | `currentQuestion` 与重播查询都改成"必须 question 非空且 answer 空" |
| 7 | **`turns` 一行的字段整体错位**：`answer` 里装 claim id、`target_claim_id` 里装时间戳，**且 SQLite 不报错** | insert 列清单 10 列但只传 9 个值 → 值按位置左移一格 | 补齐第 10 个值并逐行加注释说明每一列；新增 `tests/turns-insert.test.ts`（真实 SQLite 插一行再读回逐字段核对） |
| 8 | 断言"少传参数会被报错"是**错的** | 实测 node:sqlite 不报错，缺的列置 NULL | 把这条测试改成钉住**真实事实**（静默错位），并说明为什么要靠"读回来核对"而不是指望数据库 |

> **#7 是本轮最危险的一条**：它不报错、不崩、库里"看起来有数据"，
> 只是每个值都不在自己该在的列上。下游表现是"同学记不住上一问""重播拿到空文本"等
> 一堆看起来互不相关的怪现象。发现路径是：先怀疑重播逻辑（#6），改完仍失败，
> 才去把行**读回来逐字段打印**——一眼看到 `answer` 列里躺着 UUID。

> **#5 的教训**：流式解析的正确性必须**按多种切片粒度**测。
> 单一切片能过不代表对，因为 bug 恰好藏在"收尾引号与后续字符落在同一个 chunk"这个边界上。

## 遗留问题

1. **前端页面未做**（按用户要求本轮只做后端）。聊天页的评审席横条 / 扫读原文思考态 / 流式光标 / localStorage 暂存都还没接。
2. `callLLMStream` 的 `tokens` 按字符数粗估（流式没有 `usage`），仅用于展示，不进评测指标。
3. `personas` 的旧数据兜底（`session_id is null`）目前只是按 `created_at desc` 取，
   一旦本地积累多轮旧人设仍可能串场；正式提交前应清一次 `data/app.db`。
4. 60s 硬断只验证了常量与代码路径，**没有真的等满 60 秒**（会占掉一次预算）；阶段 6 评测时补一次。
5. `progressOf` 的 `qTotal = min(maxTurns, personas*mainsEach)` 在席位不足 3 时会变小，
   与 `modeLabel` 文案可能不一致；留待阶段 4 状态机一起统一。
