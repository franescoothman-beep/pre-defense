# 2026-10-31 阶段 3 收尾：演示模式只允许内置样例（§3.9 前提①）

## 目标

补齐阶段 3 唯一遗留的行为缺口：

> **§3.9 前提①「只允许内置样例：`fixtures/demo/` 提供样例材料。用户上传自己的文件时上传页置灰并提示"演示模式仅支持内置样例"，不静默接手」**

现状是"说一套做一套"：角标里写着「仅支持内置样例」，但 mock 模式下上传页仍可上传任意文件，
之后才在别处报 `E_MOCK_MISS`。这正是这条角标想避免的那类问题。

## 全面分析（动手前做的判断）

### 1. 判据应该是什么？—— 内容指纹，不是 docId / 文件名

先做了一轮实测：

```
内置样例 fixtures/demo/sample-paper.docx
  size = 37384 bytes
  sha256 = 176134b28669be5e…

库里各 doc 的落盘文件：
  86322517 sample-paper.docx  176134b2…  ✅ 与内置样例相同
  bdcf0d9f sample-paper.docx  176134b2…  ✅
  ...（共 8 份哈希完全相同，但各自 docId 不同）
  4dea1335 论文终稿.pdf        c330e60c…  ✗
  演示.docx（3 份）             8e64b801…  ✗
```

结论：**docId 每次上传都新生成 UUID**（库里已有 8 份字节完全相同的 sample-paper.docx），
文件名可以随便改。只有**字节哈希**是稳定的 → 用 sha256 判定。

### 2. 拦截点放在哪？—— 必须服务端，前端只负责"不误导"

前端置灰是友好提示，不是防护。绕过办法：直接 curl、禁用 JS、改 JS、复用旧 fetch。
若服务端照单全收，mock 就会拿用户的**无关材料**去回放内置样例的剧本 ——
表现为"凭我这份简历，评委却在问论文里的 1240 条数据"。

所以**两层都做**，且服务端是真正的那一层。

### 3. 放在解析前还是解析后？—— 解析前

在 `checkUpload` 之后、`extract` 之前。不合规的文件连 pdfjs/mammoth 的初始化都不做，
省下一次解析开销，也避免把无用文件写进内存深处。

### 4. 拦住之后必须给下一步

只拦住不给入口，比允许上传更糟：用户什么都点不了。
所以加了 `GET /api/demo`（只在 mock 模式提供）+「用内置样例开始 →」按钮，
且**只返回已抽过 claims 的样例**——否则用户点进去会撞上第二个失败点（`E_NO_CLAIMS`）。

### 5. 真实模式不能被一起收紧

`checkDemoOnly` 只在 `MOCK_LLM=1` 时生效。真实模式必须接受任何合法 PDF/DOCX ——
那是产品本体，不能因为"演示模式有约束"就把真实模式一起锁死。有专门的测试钉住这条。

## Bug 与修复过程（真实记录）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 材料列表里出现**一排一模一样的 `sample-paper.docx`**（截图里 10 条） | 每次上传都新建 docId（UUID 不同），库里就是多行。演示时反复重启反复上传，问题被放大 | `documents` 加 `content_hash` 列 + `GET /api/docs` 按 `coalesce(content_hash, id)` 分组去重。老数据 hash 为 NULL 时按 id 兜底，不会误合并 |
| 2 | **去重把有用的那条删掉了**：留下的 `8b04f827` 是 `claims:0`，而真正能演示的 `86322517` 有 12 条 claims 被挤掉 | 第一版按"最新"保留。用户点进去发现没有质疑点，还得重新抽一次 | 排序键改为 **claims 数降序 → 创建时间降序**。去重的目的是"别让同一份材料占多行"，不是"把有用的那行删掉" |
| 3 | `— 页 / 373 字` 读起来像数据缺失 | `pages` 为 null 是 DOCX 的正常状态（无物理页），被 `?? '—'` 兜成破折号 | 改成 `无物理页`。**"没有这个字段"与"这个字段的值是零"必须分开表达** |
| 4 | 历史 documents 的 `content_hash` 为 NULL | 迁移只对新上传的行写 hash | 写了一次性回填脚本（读 uploads 文件算 sha256 写回），13 行全部补齐后删除脚本 |

> **#2 是本轮最有价值的一条**：它说明"去重"这个动作本身带着一个**方向性选择**——
> 保留哪一条？如果只想着"去掉重复"，很容易顺手留最新的一条，
> 结果把唯一有用的数据删了。**任何"保留其一"的逻辑，都要先问"哪一条对用户最有用"。**

> **#3 也值得记**：`pages: null` 不是"没数据"，是"这种格式没有物理页"。
> 用破折号兜底会让用户以为解析失败。**"缺失"和"不适用"是两件事。**

## 遗留问题

1. **真实模式下的列表去重也会生效** —— 同一份文件传两次只显示一条。
   这是有意的（避免重复），但若用户想"同一份材料开两场不同会话"，
   需要的是新 session 而不是新 doc，所以不影响。
2. `content_hash` 回填脚本是一次性跑的，已删除；**新上传自动写 hash**，无需再跑。
3. `/api/demo` 只返回 `DEMO_FILES[0]`（当前只有一份样例）。将来多份样例时要改成遍历。
4. 前端 `mockMode` 靠 `/api/health` 读；若 health 挂了会按真实模式展示（宁可多给入口，不误锁）。
