# 阶段 4：判分 / 追问 / 状态机 / 安全基线

> 日期：2026-11-01｜commit：`feat: grading + followup state machine + security baseline`
> 对应 `开发流程详细文档.md §阶段 4`，DoD 六条全部达成。

## 一、目标

把阶段 3 的"能出题"接到"能闭环"：用户答完 → 判分 → 机检 → 决定追问 / 换人 / 出报告。
这一阶段结束时，`quick` 档必须能跑完"上传 → 三问 → 报告"整条链路，且报告永不缺席。

## 二、做了什么

### 1. `lib/prompts/evaluate.v1.ts`（新）

五档判分写死（5 = 答清了 / 3 = 方向对但关键处含糊 / 0 = 空答），并要求**先写 gaps 再定 score**——
顺序反过来时，理由会退化成对分数的粉饰。

`locators` 下限 1 条是逼模型编引用的入口。缓解手段是 prompt 侧给足出口：
有可引用句 → quote 类逐字复制；压根没有 → absence 类给 scope。
两者都是"合法出处"，不合法的是"编一句原文里不存在的话"。

追问只能咬同一条质疑点，`target_claim_id` 必须从候选清单原样复制，
服务端还会做归属校验（见 `lib/grade.ts`）——宁可少问一次，不用假锚点。

### 2. `lib/state.ts`（改）

三处改动，每处对应一个真实会踩到的坑：

| 改动 | 之前 | 之后 | 为什么 |
|---|---|---|---|
| `round` 语义 | `ceil(seq/judges)` | 主问序号（追问继承） | quick 档 3 个主问全塞进 round 1，"本轮追问几次"永远算错 |
| `quick.followupsEach` | `0` | `1` | 旧值意味着**默认档永远不会有追问**，而"轮番提问与追问"是名字的一半 |
| 新增「主问配额用尽即收口」 | 无 | `mainsDone >= mainsNeeded → end` | C11「报告永不缺席」与 DoD「第 3 问后必然进报告」的落点 |

另补 `judgesOf()`：材料维度不足时只有 2 位评委，旧实现会一直空等到第 3 位，直到撞轮次上限。

### 3. `lib/grade.ts`（新）

判分结果的"洗数据"层，纯函数：

- `gradeLocators`：逐条过 `attachLocator`；越界丢弃，未命中**保留**（进分母）
- `verifiedOkOf`：至少一条出处通过机检才算"可溯源"；absence 有合法 scope 也算通过
- `validateFollowup`：归属校验。模型编的 id / 指向别的主问已问过的点 → 作废
- `roundOfSeq` / `roundOfLegacy`：新旧 round 口径的转换与兼容

### 4. 三条新路由

| 路由 | 职责 | 关键约束 |
|---|---|---|
| `POST /answer` | 判分 → 机检 → 写 turns → 决定下一步 | turnId 必须属于本场、不许重复提交、判分失败不吞答案 |
| `POST /next` | 换评委 / 收口 | 幂等：只读 turns 表，不写"进度指针" |
| `POST /end` | **任何状态可调**，立刻出报告 | 幂等（先查已有报告）、无模型也能出（退回模板） |
| `GET /reports/:id` | 读报告 + 审议轨迹 | 只读，不改一个字符 |

`/end` 的降级设计是这一阶段最重要的一条：模型挂了、预算烧光、还没作答——全都能出报告。
字段结构完全一样，只是 comment 换成服务端算出来的事实句。
一份字段齐全、数字正确、文笔朴素的报告，远胜于"报告生成失败"的空白页。

### 5. 前端接线

聊天页接上 `/answer`（不再禁用按钮）、追问就地展示（不走 SSE，省一次预算与一次延迟）、
三种 decision 都分支、缎带上常驻「结束并出报告」。
报告页做了**阶段 4 最小可用版**：两栏（材料风险 / 临场表现）+ 极性标注 + 高风险清单 + 审议轨迹，
并显式写出"本页尚未完成的部分"（看板 / 复练 / 引用脉冲）。

## 四、真实 Bug 与修复过程（8 条）

### Bug 1：`attachLocator` 靠错误文案判断越界，短 quote 绕过

`verifyQuote` 是**先查长度、后查范围**，所以「block_idx=99 + quote 只有 6 字」先返回"quote 过短"，
越界判定根本没执行到。若只判断 `reason === 'block_idx 越界'`，这条越界 locator 会被当成正常条目落库——
`blockIdx` 存成 99，前端拿它去 blocks 表取原文只能拿到空，界面上是一条点不开的引用。

**修法**：在 `attachLocator` 入口直接判边界，与校验函数内部的检查顺序无关。

### Bug 2：`verifyAbsence` 的 scope 匹配方向写反

旧实现 `norm(section).includes(norm(scope))` —— 拿章节名去包含 scope。
但模型给的 scope 通常**更长**（"2. 数据与方法：三所学校的办学性质…"），永远 false，
一条明明合法的 absence 被判"未落在已知章节"，**缺失类检索覆盖率被白白压低**。

**修法**：双向匹配（scope 含章节名 / 章节名含 scope），并去掉全部空白再比。
但双向不能无脑放宽——只写 `scope.includes(section)` 时，任何含"1"这种单字章节的 scope 都会命中，
覆盖率会变成恒 100% 的假指标。所以加门槛：**scope 一侧 ≥2 字**；
章节名一侧**不设长度门槛**（"摘要""引言"是真实存在的 2 字标题，
用"太短"去拦它等于宣称"你这篇论文没有摘要"）。

### Bug 3：`next build` 失败——路由文件多导出一个常量

`export { FALLBACK_FOLLOWUP }` 让 Next 报
`Property 'FALLBACK_FOLLOWUP' is incompatible with index signature`：
路由模块被当成「只许导出方法」的约定对象。

**这条 `npm test` 与 `tsc --noEmit` 都发现不了——只有真正跑 build 才会暴露。**
修法：路由文件只导出 Next 认得的符号。

### Bug 4：`.env.local` 是真实模式，但服务报 `mock: true`

改动前先查出**端口 3111 上是昨天 23:14 启动的旧进程**（PID 29052），它加载的是旧构建与旧环境。
我的新进程因 `EADDRINUSE` 没绑上端口，于是"验证"验的是过期产物。
**这正是 progress.md 里那条"改代码后必须核对新 PID 启动时间晚于构建时间"的现场。**

### Bug 5（最贵的一条）：报告的 `locators` 写成纯字符串数组，整份报告报废

真实 key 跑 `/end`，模型返回：

```json
"locators": ["我们认为该结论可以推广到全市乃至全省的课后服务管理场景"]
```

约定是 `[{kind, block_idx, quote}]`。zod 校验失败 → `/end` 静默降级成模板。
**而那份被丢掉的原始输出质量其实很高**：四维评语、8 条高风险清单、advice 全部到位。
一个形状瑕疵让一整份好报告报废。

**两处修法**：
1. prompt 侧：原来只写"格式与判分时一致"（自述式说明，在多段式 prompt 里就是会失效）。
   改成把对象形状逐字段写出来，并给出**正例与反例**——模型对反例的敏感度高于规则。
2. schema 侧：`ReportLocatorIn` 允许字符串，规整成 `{quote, block_idx: -1}`。
   `-1` 是"位置未知"的哨兵，交给机检判 → `verified=0`，**绝不会被当成合法出处**，
   且进入命中率分母。容错与编数据的界线就在这里。

配套新增 `attachReportLocator`：位置缺失时**保留 quote、标"位置未标注"、verified=0**。
判分链路越界该丢（拿它取原文只能拿到空），但报告里那句引文仍有信息量——
它是"模型在批评材料里的哪一句话"。丢掉它，报告可读性直接砍半。

### Bug 6：`material_risk` 给 5 条（某维写两遍），二次降级

第二次实测在同一处再挂：`Too big: expected array to have <=4 items`。
模型把某个维度写了两遍。

**简单 `slice(0,4)` 是错的**：它可能留下第一条潦草的、丢掉后面那条更具体的，
而且丢掉哪一维完全取决于模型输出顺序。**按 dimension 去重**才是对的语义，
保留评语更长的那条（信息量更大）。同理 `performance` 去重时保留**更低**的分——
临场表现是越大越好，模型重复给分说明它自己也没定，此时取保守值，避免美化。

`high_risk` 则相反：它的语义是"按危险排序的前 N 条"，**截断是对的**。
`EvaluateOut.gaps/locators` 也给同样容错，但 `locators.min(1)` **不许放松**——
"每条评价 ≥1 条出处"是 anchor-verified 的硬承诺。

### Bug 7：报告自相矛盾——risk_score=58 旁边写"本场未覆盖技术深度"

实测报告里出现：`depth` 维 `risk_score=58`（服务端聚合出的真实数字），
评语却说"本场未覆盖技术深度维度"，`performance` 里 depth 也是 null。而用户明明被 depth 评委问过。

根因：两栏共用了一个 `askedDims` 集合，而 **两个 "covered" 是不同的事**：

| 栏 | covered 的含义 | 判据 |
|---|---|---|
| 左栏 材料风险 | **材料**在这一维有没有质疑点 | `risk_score !== null` |
| 右栏 临场表现 | **本场**有没有在这一维问过 | 评委维度 ∈ 本场已问 |

进一步，`askedDims` 原来是按 **claim 的 dimension** 收集的，
而评委席位按 (维度, 类型) 排，问题 targeting 的 claim 维度与评委负责的维度并不总一致。
改成**按评委维度**收集——用户感知的就是"我被几个不同视角的评委问过"。

UI 上也把两个"未覆盖"分开标：`材料无此维` vs `本场未问到这一维 · 切 full 档可覆盖`。

### Bug 8：`progressOf` 两个同名函数返回不同结构

`lib/state.ts` 与 `lib/session.ts` 各有一个 `progressOf`（一个吃内存快照、一个查库），
返回字段不一致（一个没有 `qIndex`）。路由与测试各写一套取字段逻辑，迟早分叉。
**修法**：state 版补齐 `qIndex/qTotal`，两处结构对齐。
